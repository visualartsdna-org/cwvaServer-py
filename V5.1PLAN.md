## Item 4 — Alphabetical collection members

### Current behavior

`services/rdf2html.py` emits one row per `skos:member`, iterating `uri_list` in
graph order — effectively arbitrary.

### Approach — ORDER BY at retrieval

Ordering is done in SPARQL rather than in Python wherever a query is involved.

`query_collection()` in `rdf/query_support.py` gains `ORDER BY ?label`, and the
caller iterates the returned mapping (Python dicts preserve insertion order)
instead of iterating its own `uri_list`.

**Correctness detail — do not skip.** The existing query is:

```sparql
SELECT ?uri ?label WHERE {
    VALUES ?uri { ... }
    { ?uri rdfs:label ?label } UNION { ?uri skos:prefLabel ?label }
}
```

There is no `OPTIONAL`, so a member with **no** label produces no row at all.
Today that is harmless — the caller iterates `uri_list` and falls back to
`_short()` for anything missing from the map. If the caller switches to
iterating query results, unlabeled members are silently **dropped from the
page**.

**Decided: `OPTIONAL` + `COALESCE`.** Every member returns exactly one row and
a single `ORDER BY` covers the whole set — no Python-side merge of a second
group.

**Status: IMPLEMENTED AND VERIFIED.** Final query:

```sparql
SELECT ?uri ?label WHERE {
    { SELECT ?uri WHERE { VALUES ?uri { ... } } }
    OPTIONAL {
        { ?uri rdfs:label ?l0 } UNION { ?uri skos:prefLabel ?l0 }
    }
    BIND(COALESCE(?l0, STR(?uri)) AS ?label)
} ORDER BY LCASE(?label)
```

The obvious form of this query — bare `VALUES` plus two sequential
`OPTIONAL`s — **does not work on RDFLib 7.6.0**. Two distinct defects were
found and isolated during implementation:

1. **`VALUES` + `OPTIONAL` is evaluated as an inner join**, not a left join.
   Every URI with no matching triple is silently dropped — precisely the bug
   this rewrite was meant to prevent. Confirmed minimally: bare
   `SELECT ?uri { VALUES ?uri { <A> <Absent> } }` returns both, but adding
   `OPTIONAL { ?uri rdfs:label ?l }` returns only `<A>`. **Fix:** wrap the
   VALUES in a subselect.
2. **Two sequential `OPTIONAL`s lose the second binding** — URIs carrying only
   `skos:prefLabel` were dropped. **Fix:** one `OPTIONAL` containing a `UNION`.

A `UNION` of matched/unmatched branches was also tried and raises
`TypeError: '<' not supported between instances of 'NoneType' and 'tuple'`
inside RDFLib's ORDER BY. Avoid that shape.

Three further details:

- **`BIND` rather than a `SELECT` expression alias.** `ORDER BY` precedes
  projection in the SPARQL evaluation sequence, so a SELECT-clause alias is not
  reliably visible to `ORDER BY`.
- **`LCASE`** — bare `ORDER BY ?label` is codepoint order, sorting all
  uppercase ahead of all lowercase.
- **`STR(?uri)` as final fallback** guarantees a total order even for an
  unlabeled member. The caller substitutes `_short()` when the returned label
  equals the URI, preserving the existing CURI appearance.

Return type stays `dict` — it de-duplicates URIs carrying multiple labels and
preserves SPARQL ordering through insertion order.

These RDFLib behaviors are now recorded in `CLAUDE.md`; item 3's batched
object-label helper will hit the same constructs and should reuse this shape.

### Verification performed

Against the real store (45,148 triples, full load with inference and policy):

- `cwvaClassCollection` — 321 members requested, 321 returned, alphabetical, 0 unlabeled
- `paintingTermCollection` — 280 requested, 280 returned, alphabetical, 0 unlabeled
- `WatercolorCollection` rendered end-to-end through `rdf2html.process()` — 173

- Regression: `/work/{guid}` AI criticism, `/model/CreativeWork`, and the

Formal QA remains with the repository owner.

### Where ORDER BY does not apply

`_build_rows()` walks `main_g` — a CONSTRUCT subgraph — via
`graph.predicate_objects()`, not SPARQL, so there is no query to order. The
ordering therefore has to come from `query_collection()`, which does run a real
SPARQL query against the full graph. That satisfies "ORDER BY on retrieval
where possible."

Already correct, no change needed: `query_tags()` (`ORDER BY ?l`) and
`query_collections()` (`ORDER BY ?label`).

### Cleanup

Delete the unreachable `skos:member` branch in `_render_pred()`. `_build_rows`
intercepts the identical condition earlier and `continue`s, so the branch
cannot execute. **Confirmed for removal.**

## Item 3 — Labels for ObjectProperty values

### Current behavior

`_render_one()` falls through to a linked `_short(val, ns_map)`, so
`vad:hasComposition the:DynamicEquilibrium` renders as the CURI
`the:DynamicEquilibrium` instead of "Dynamic Equilibrium".

`metacontent/model/cwva.ttl` declares 45 `owl:ObjectProperty` terms, including
`vad:hasWatercolorPaint` and `vad:hasComposition`.

**Status: IMPLEMENTED AND VERIFIED.**

### Approach

Extend the existing per-page batch mechanism. `_fetch_prop_labels()` already
issues one `VALUES` query per page against the full `rdfs` graph; add a
companion projection returning which predicates are `owl:ObjectProperty`.
In `_render_one()`, when the predicate is an ObjectProperty, use the object's
label as anchor text, falling back to the CURI when no label exists.

### Governing rule (decided)

> If a property object or collection member is **discretely anchored** —
> rendered as its own standalone link — the anchor text is its label.

Applied uniformly, with no per-predicate exceptions. Values that are not
discretely anchored (images, the model-viewer embed, plain-text properties)
early-return before the general rule and are untouched.

### Key finding — the ObjectProperty signal is wider than expected

`metacontent/model/schemaSupplement.ttl` contains an "rdfs hardening" block
that deliberately declares the structural predicates `rdf:type`,
`rdfs:subClassOf`, `rdfs:seeAlso`, `rdfs:isDefinedBy` and
`skos:broader/narrower/related/inScheme` as `owl:ObjectProperty` — so they pick
up labels in the *property* column. The store therefore reports **71**
ObjectProperty terms, not the 45 `vad:` domain properties in `cwva.ttl`.

Under the discrete-anchor rule these all get labelled values, which is the
intended outcome. Verified changes:

| Page | Row | Before | After |
|---|---|---|---|
| AI criticism | `type` | `the:AI, skos:Concept, the:Entity, rdfs:Resource` | `AI, skos:Concept, Entity, rdfs:Resource` |
| `/model/CreativeWork` | `subclass of` | `vad:Art, vad:ArtRealization, …` | `Art, Art Realization, Visual Arts, Creative work` |
| `/thesaurus/Watercolor` | `broader` | `the:Painting, the:ArtForm` | `Painting, ArtForm` |
| AI criticism | `has composition` | `the:DynamicEquilibrium` | `Dynamic equilibrium` |

### TODO — label the structural classes in schemaSupplement.ttl

`skos:Concept`, `rdfs:Resource`, `rdfs:Class` and `owl:Class` carry no
`rdfs:label`, so type rows mix labelled local terms with CURI external ones
(`AI, skos:Concept, Entity, rdfs:Resource`). Add labels to the "rdfs hardening"
block in `metacontent/model/schemaSupplement.ttl`:

```turtle
skos:Concept  a owl:Class ; rdfs:label "Concept" .
rdfs:Resource a owl:Class ; rdfs:label "Resource" .
rdfs:Class    a owl:Class ; rdfs:label "Class" .
owl:Class     a owl:Class ; rdfs:label "Class" .
```

Type rows then read `AI, Concept, Entity, Resource`. Data-only change, no code.

**Coordination:** this file lives in `metacontent/`, which is fetched from
`referenceModel` — the change must land on the reference server (visualartsdna.org)
or other deployments will not pick it up. Same constraint as the `vad:video`
addition in item 2.

### Rule qualification — objects with a label property

The discrete-anchor rule is qualified: an object is anchored by its label **only
when it carries one**. Implemented as `_label_or()` in `services/rdf2html.py`.

This future-proofs the document predicates. Today `the:mdDocument` (76 distinct
objects) and `the:pdfDocument` (55) are plain document URIs with **zero** labels
between them, so both continue to display filenames — no visible change. If a
document object later becomes a complex object carrying a label, it will be
anchored by that label automatically with no code change.

**Relevant to item 2:** `schema:video` → `schema:VideoObject` would carry
`schema:name`, not `rdfs:label`. `schema:name` has **0 triples** in the store
today, and `query_labels()` unions only `rdfs:label` + `skos:prefLabel` — so
adopting VideoObject requires adding `schema:name` to that union **and** to the
`sh:alternativePath` in `res/labels.shacl`, or video objects will render as
CURIs and be reported as unlabelled.

### Two constraints

**Query the full graph.** Property type declarations live in the ontology, not
in `main_g`. Use `qs.graph` (the `rdfs` store); `main_g` is a CONSTRUCT subgraph
and contains none of them.

**Batch the object label lookups.** A single detail page can carry a dozen
ObjectProperty values, and collections carry far more. Calling `query_label()`
per value is N queries per page. Add a batched helper modeled on
`query_collection()` — one `VALUES` query for all object URIs on the page —
and resolve from that map.

### Consolidation (done)

Verified in the loaded store before deleting anything — all five are declared
`owl:ObjectProperty`:

| Predicate | Declared types |
|---|---|
| `vad:hasArtistProfile` | ObjectProperty, Property, Resource |
| `vad:artist` | ObjectProperty, Resource, Property |
| `vad:background` | ObjectProperty, Resource, Property |
| `vad:pseudonymFor` | ObjectProperty, Resource, Property |
| `the:tag` | ObjectProperty, SymmetricProperty, Property, Resource |

`_ARTIST_PREDS` and the `the:tag` branch are therefore removed — the general
rule covers both. `CLAUDE.md` records that future label special cases should be
handled by declaring the property `owl:ObjectProperty` in the ontology rather
than adding a predicate list to the renderer.

Also removed: the now-unused `is_collection` parameter on `_render_pred()`,
left dead by item 4.

### Files

- `services/rdf2html.py` — ObjectProperty detection, general label rule, remove
  `_ARTIST_PREDS` and the `the:tag` branch
- `rdf/query_support.py` — batched object-label helper
- `CLAUDE.md` — property rendering table

Widest visual blast radius in the cycle — every detail page changes. No data or

### Multi-value ordering — IMPLEMENTED

Rows carrying several ObjectProperty values now render alphabetically by the
text the reader actually sees, sorted in `_render_pred()`. RDFLib graph
iteration order is arbitrary — neither source order nor stable between loads —
so this also makes page output deterministic.

Literal-valued predicates are deliberately **excluded**: source order can carry
meaning in prose, and sorting several `skos:note` values would scramble it.

Verified on the AI criticism page: `has process`, `has sculpture term`,
`has tensegrity art principle`, `tag`, `topic` and `type` all sorted. `type`
now reads `AI, Entity, rdfs:Resource, skos:Concept`.

**`the:mdDocument` / `the:pdfDocument`** are discretely anchored but display the
filename rather than a label, since those documents carry no `rdfs:label` and
the filename is the meaningful identifier. They participate in the sort.

## Item 5 — model/vocabulary label integrity check

**Status: SHAPE DELIVERED as `res/checks/labels.shacl`. NOT wired to anything —
awaiting migration to the dashboard.**

### Scope decision — this is a metacontent check

Originally framed as a data-quality report run during the load. That framing was
wrong, and the first run proved it: **all 32 results were `model/` (4) and
`thesaurus/` (28) terms — zero `work/` instances.** Missing labels are an
ontology and vocabulary concern, not a user-data concern.

The check therefore belongs where the ontology and vocabulary are maintained,
run after the model or vocabulary is modified — not on every server start and
`/refresh`, where it taxed every deployment for a condition user data cannot
cause.

### Current state

- Shape lives at `res/checks/labels.shacl`, deliberately **outside** the
  `res/*.shacl` glob that `db_mgr._validate()` runs. Nothing invokes it.
- `db_mgr.py` is back to its original form — the per-file advanced-mode
  detection and the `shaclAdvanced` config flag were both removed as dead
  machinery once the shape left the load path.
- Load time returned to baseline (~32s).
- Verified still correct when invoked directly: 13.2s, `Results (32)`.

### TODO — migrate to the dashboard

Run after ontology or vocabulary modification. Two requirements the
implementation must honor, both confirmed empirically:

1. **`advanced=True` is mandatory.** The shape uses a SPARQL-based target. With
   advanced mode off, pyshacl does not error — it reports `conforms=True` with
   zero results. The check would appear to pass while checking nothing.
2. **Validate the inferred `rdfs` store.** `?p a owl:ObjectProperty` comes from
   the schema store; the non-inferred `data` store yields zero targets.

```python
conforms, _, report = pyshacl.validate(dbm.rdfs, shacl_graph=shapes,
                                       advanced=True)
```

Budget ~13–15s per run. The cost is the target query — `?p a
owl:ObjectProperty . ?s ?p ?this` with all three terms unbound is a full scan
joined against 71 properties, measured at 16.5s in raw RDFLib outside pyshacl.
Narrowing the target to only unlabelled nodes did not recover it; the scan
dominates. Fine for an on-demand check, which is the reason it left the load
path.

### Design

Target: objects of `owl:ObjectProperty` triples that are IRIs and carry no
label; constraint: `sh:minCount 1` on `sh:alternativePath (rdfs:label
skos:prefLabel)` — the same union `query_labels()` uses. The shape conforms when
the data is clean, since a clean dataset produces an empty target set.

A SHACL Core alternative using `sh:targetObjectsOf` (one shape per object
property, ~45 shapes) would avoid advanced mode but needs editing every time the
ontology grows. Rejected.

### Resolved during implementation

**Which store — settled, not a choice.** The shape *must* run against the
inferred `rdfs` store. `?p a owl:ObjectProperty` comes from the schema store, so
the non-inferred `data` store yields **zero** targets. Measured both.

**Noise control — measured.** Scoping took the report from unusable to
actionable:

| Scope | Distinct objects |
|---|---|
| All unlabelled ObjectProperty objects | 1,249 |
| Restricted to `visualartsdna.org` | 885 |
| Also excluding non-anchored predicates | **32** |

The 885 → 32 drop is almost entirely `/images/*` URIs reached via
`schema:image`. Those render as `<img>`, never as a labelled anchor, so an
absent label is not a defect. The shape excludes `schema:image`, `vad:image3d`,
`vad:qrcode`, `the:mdDocument` and `the:pdfDocument` for that reason — it
reports exactly the cases where the renderer would fall back to a CURI.

**Performance — the reason it left the load path.** Documented under "TODO —
migrate to the dashboard" above. Two intermediate mitigations (per-file advanced
mode detection, and a `shaclAdvanced` config flag) were built and then removed
when the check moved out of the load entirely — they are recorded here only so
the approach is not re-derived later.

### Verification performed

- Shape parses; report reads `Results (32)` — exactly matching an independent
  SPARQL probe of the same condition
- 32 distinct focus nodes, no duplicates, clean CURIs in the report
- `advanced=False` → conforms, zero results: confirms the plan's warning that
  the shape is silently inert without advanced mode
- Load times measured both ways (31.3s off / 45.9s on)
- Existing three shapes still pass and stay on the fast path (0.1–0.2s each)

### The 32 findings

Four are ontology classes (`model/ConceptualAnalysis`, `model/DigitalImage`,
`model/PaintApplicationImage`, `model/Proof`). The rest are thesaurus terms,
including several watercolor techniques (`wetOnWet`, `flatWash`, `softEdge`,
`hardEdge`, `drybrushTechnique`, `layering`, `blotting`, `coldPressed`,
`atmosphericPerspective`, `washVariegated`, `wetIntoDryWash`,
`pressingintowetpaper`, `Lifting`), pigments (`AlizarinCrimson`, `VirdianLCS`,
`OtremarineDD`), AI platform entities (`ChatGPT`, `ClaudeAI`,
`AIAssistedCriticism`), and structural terms (`entities`, `forOntology`,
`forThesaurus`, `relatedBlogPosts`, `HistoricalPigmentsScheme`).

## Item 2 — MP4 video support

**Status: IMPLEMENTED AND VERIFIED.**

Predicate is **`schema:video`**, not `vad:video` as originally planned —
`schema:` is already the namespace for image, dimensions and `contentUrl`, and
it admits the richer VideoObject form. Both authoring shapes are supported:

```turtle
schema:video <http://visualartsdna.org/media/turntable360.mp4> .

schema:video [ a schema:VideoObject ;
               schema:contentUrl <http://visualartsdna.org/media/clip.mp4> ;
               schema:name "360 degree turntable view" ] .
```

The VideoObject's `schema:name` renders as a caption. Supporting both means the
simple case stays a one-liner while complex objects work without a later
migration — the reason for the `_label_or()` qualification made in item 3.

Largest item in the cycle; sequenced last. Three separable pieces.

### 2a. Ontology — DELIVERED

Declared in `metacontent/model/schemaSupplement.ttl` and uploaded to the GCP
bucket. Verified resident after refresh: the property row resolves to "video",
`schema:VideoObject` and `schema:name` both carry labels, and no video node is
inferred as `xsd:string`.

**`rdfs:range` is `rdfs:Resource`, deliberately — do not "correct" this to
`schema:VideoObject`.** schema.org gives `video` a range of `VideoObject`, and
that was tried, but RDFS inference turns a range into an assertion:

```
work:x schema:video <clip.mp4>   ⟹   <clip.mp4> a schema:VideoObject
```

Two consequences, both observed on the real store:

1. A direct-URI video is then inferred to be a VideoObject, so
   `res/video.shacl` demands `rdfs:label` and `schema:contentUrl` from a plain
   `.mp4` URL — two violations per video, logged at every load.
2. The false triple is published. `<clip.mp4> a schema:VideoObject` states that
   the *file URL* is a VideoObject, and that flows into `/data`, `/rdfs` and
   every RDF export for consumers to take at face value.

The model deliberately permits a bare URL, which schema.org's range does not.
`rdfs:Resource` matches `schema:image` and `schema:contentUrl` in the same file
and keeps both authoring forms valid — the dashboard is expected to always
write a VideoObject, but CE authors are not forced to.

Declarations:

```turtle
schema:video  a owl:ObjectProperty ;
    rdfs:label "video" ;
    rdfs:range rdfs:Resource ;
    rdfs:comment "A video of the work. Either a direct URL to the video file, or a schema:VideoObject carrying schema:contentUrl and schema:name." .

schema:VideoObject  a owl:Class ;
    rdfs:label "Video Object" ;
    rdfs:comment "A video file with its own metadata — content location, label, and any further description. Requires rdfs:label; schema:name is optional." .

schema:name  a owl:DatatypeProperty ;
    rdfs:label "name" ;
    rdfs:range xsd:string ;
    rdfs:comment "The schema.org name of a resource. Optional on schema:VideoObject, where rdfs:label is the required label." .
```

**Labelling convention (decided):** a `schema:VideoObject` always carries
`rdfs:label`; `schema:name` is optional and may hold the same literal or a
different one. `rdfs:label` is the site-wide label predicate and supplies the
player caption; `schema:name` is schema.org interop, used as a caption fallback
only when `rdfs:label` is absent. Enforced by `res/video.shacl` — SHACL Core,
runs at load, no advanced mode.

**⚠ Local edits to `metacontent/model/` do not survive a server start.**

The production config sets `referenceModel: null` **and** `cloud` with
`clobber: true`. With `referenceModel` null, `_clear_synced_folders()` in
`db_mgr.py` includes `model/` and `vocab/` in the folders it deletes before
each load, then GCP sync repopulates them from the bucket — the bucket is the
sole source of truth for metacontent in this deployment.

This was observed, not theorised: the declarations above were applied locally
and verified working, then destroyed by the next ordinary server start.

Delivery therefore requires **the GCP bucket**, not just the working copy:

1. Edit `metacontent/model/schemaSupplement.ttl`
2. Commit and push it to `cwvaMetacontent` (version control)
3. **Upload it to `gs://$GCP_BUCKET/ttl/model/schemaSupplement.ttl`** — this is
   the step that makes it survive, and the one easily forgotten

Note the earlier framing in this document — "must land on the reference server
(visualartsdna.org)" — is wrong for this deployment. It would apply only to a
config with `referenceModel` set, which is the CE bootstrap path, not this one.

Until the ontology lands, `schema:video` still renders correctly; the row label
falls back from "video" to the CURI `schema:video`. Nothing else degrades.

Current data has no video predicate — MP4 is referenced only in prose inside
`skos:definition` on two instances. Data authoring follows the schema change.

### 2b. Serving — the substantive work

`.mp4` is absent from `IMAGE_SUFFIXES` in `servlet_base.py`. **Adding it there
is the wrong fix**, for two reasons:

1. **No HTTP Range support.** The image handler does
   `Response(content=file_path.read_bytes(), …)` — no `Accept-Ranges`, no `206
   Partial Content`. Browsers issue Range requests to seek within video;
   without them scrubbing fails and some browsers refuse to begin playback.
2. **Memory.** Reading a 50 MB MP4 fully into memory per request is untenable
   on the e2-micro free-tier target named in ROADMAP.

Implement a **separate `/media/{filename}` route** using `StreamingResponse`
with Range parsing, rather than extending the image whitelist.

Keep `.mp4` **out** of the thumbnails path — `serve_thumbnail` shares the same
suffix set and would hand an MP4 to Pillow.

`util/gcp.py` needs on-demand fetch for the new media type, following the
existing image/document pattern.

### 2c. Rendering — native `<video>` (decided)

No video.js. A plain `<video controls>` element in a container div, consistent
with the framework-free style of the rest of the site and avoiding a ~150 KB
dependency for behavior every current browser provides natively.

New case in `_render_one()` keyed on `vad:video`, following the shape of the
existing `vad:image3d` handling.

### Verification performed

Range behaviour, against a 1 MB fixture with verifiable byte content:

| Case | Result |
|---|---|
| Full GET | 200, `Accept-Ranges: bytes`, body byte-identical |
| `bytes=0-1023` | 206, `Content-Range: bytes 0-1023/1048576`, bytes match |
| Mid-file seek `bytes=500000-500999` | 206, correct slice |
| Open-ended `bytes=1048000-` | 206, 576 bytes, correct tail |
| Suffix `bytes=-1024` | 206, correct final 1 KB |
| Past EOF | 416 with `Content-Range: bytes */1048576` |
| Malformed `bytes=abc-def` | falls back to full 200 |
| `HEAD` | 200, `Content-Length` + `Accept-Ranges`, no body |
| `.mp4` via `/images` | 403 |
| Path traversal, raw and percent-encoded | 403 / 404 |

Rendering, both authoring forms injected into the loaded store:

- Two `<video>` elements rendered, sources root-relative to `/media/`
- VideoObject `schema:name` used as caption
- Blank-node VideoObject **not** flattened into recursive sub-rows
- `/images/*.mp4` URI rerouted to `/media/`
- Row label "video" resolved from the ontology
- No video.js anywhere in the output

Two defects found and fixed during testing:

1. **`HEAD` returned 405.** FastAPI does not derive HEAD from a GET route.
   Registered explicitly and short-circuited so the body generator never runs.
   Players issue HEAD to learn length and range support before seeking.
2. **Path traversal.** `Path(media_dir) / filename` with `..` could reach files
   outside the media folder (limited to video suffixes by the extension check,
   but still an escape). Added a `is_relative_to(base)` containment check that
   refuses and logs. **Note `/images/*` has the same pattern and was not
   changed** — out of scope here, worth a separate look.

### Risk

Range/streaming was the only genuinely new server mechanism in this cycle.
Seeking was tested explicitly, not just playback start — a video that plays from
0:00 but cannot be scrubbed is the characteristic Range failure.

Not exercised: a real MP4 in a real browser. The fixture is synthetic bytes with
a `.mp4` extension, which validates the transport but not codec playback. Worth
a manual check with an actual file during QA.
